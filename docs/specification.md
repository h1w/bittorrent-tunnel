# AmneziaWG под BitTorrent: спецификация MVP

## Статус

Исследовательская спецификация, не готовая реализация. Цель — маскировка AmneziaWG под загрузку/раздачу BitTorrent против пассивного DPI. Активное зондирование исключено владельцем. Звонки и онлайн-игры обязательны. Нельзя обещать универсальную неотличимость, нулевые задержки или прохождение неизвестного DPI.

Главный результат проверки: испытанная pure-Go реализация µTP при выбранной нагрузке не выполнила целевую прибавку p95 RTT <=20 мс относительно UDP. Сравнение с прямым AWG не выполнено. Реализация полного продукта не должна начинаться с предположения, что транспорт уже удовлетворяет требованиям.

## Поставка

Два самостоятельных бинарника для Linux amd64/arm64: `btawg-server` на VPS и `btawg-client` на устройствах. Сервер содержит веб-панель, API, встроенное транзакционное хранилище, AmneziaWG и внешний транспорт. Клиент — импорт конфигурации, TUN, AmneziaWG, discovery и транспорт. Внешние торрент/AWG-процессы не требуются. Для настройки TUN, маршрутов и firewall необходимы права Linux; один бинарник не устраняет эти требования.

Основной язык-кандидат — Go с официальным amneziawg-go. Rust возможен, но интеграция Go-движка требует FFI/runtime либо иной проверенной реализации. Конкретные версии зависимостей фиксируются перед реализацией. Криптографию самостоятельно не переписывать.

## Требования к каналу

Путь: приложение → TUN → AWG → адаптер conn.Bind → внешний транспорт → VPS → AWG → маршрутизация.

Датаграммы сохраняют границы. Служебные AWG-пакеты также проходят внешний транспорт; прямой AWG fallback запрещён. µTP/UDP — исследуемый основной транспорт, TCP — резерв с отдельной оценкой пригодности для real-time. Оба упорядочены и могут задерживать следующие данные при потерях.

DHT BEP5 используется для обнаружения адреса VPS, а не как VPN-релей. Кандидат адреса недоверенный; сервер проверяется закреплённым AWG-ключом. DHT и bootstrap не находятся на пути каждой датаграммы. Недоступность DHT без известного адреса должна давать явную ошибку. Не обещать обход блокировки IP VPS.

Маскировка требует не только узнаваемого handshake: проверяются состояния interested/choke/unchoke, bitfield/have, request/piece, индексы, длины и повторные ответы. Пассивный наблюдатель может проверить содержимое при наличии метаданных. Подмена блоков AWG-данными нарушает файловые хеши. Исключение активной проверки не устраняет этот риск.

Последовательные корректные файлы с шифротекстом сохраняют хеши, но требуют своевременного объявления новых метаданных и запросов. BEP9 позволяет прямую передачу метаданных, BEP46 — обновляемые DHT-указатели; ни один сам по себе не доказывает малую задержку. Накопление файлов и искусственные паузы ради маскировки не выбираются как основной real-time канал.

**Нерешённый контракт:** конкретная конструкция, одновременно обеспечивающая требуемую пассивную маскировку и задержку. Не заменять её произвольным UDP с похожими заголовками и не называть это полноценным µTP. Прохождение nDPI само по себе не доказывает полную маскировку.

## Эксперимент 1: наблюдаемые результаты

Изолированный Go-процесс, localhost UDP-сокеты. Обёртка отправки добавляет 20 мс на направление и независимые псевдослучайные потери. Нагрузка — 300 сообщений по 256 байт с интервалом 10 мс; echo-сервер; RTT от постановки сообщения перед Write до чтения echo. Границы сообщений µTP восстанавливаются через io.ReadFull. Случайные генераторы имеют фиксированные начальные состояния, но расположение потерь в прикладных данных разных транспортов не идентично из-за разного числа служебных пакетов. Нет ограничения пропускной способности, AWG, BitTorrent-сообщений, DHT или конкурирующей загрузки. Это искусственный канал, не реальный WAN и не доказательство маскировки.

Зависимость: github.com/anacrolix/go-utp v0.0.0-20260908033909-9f1664acf866, PureGo, CGO_ENABLED=0, Go 1.27.4. Буферы µTP 64 KiB; вариант default использует целевую задержку по умолчанию, вариант 5ms — WithTargetDelay(5*time.Millisecond). Значение congestion target не является постоянной прибавкой RTT.

| localhost, без задержки/потерь | µTP 5ms | 300/300 | 0.185 | 0.308 | 1.306 |

UDP-перцентили относятся только к доставленным пакетам; нельзя трактовать их как отсутствие потерь. Единственный короткий прогон не даёт доверительных интервалов или сравнительного вывода о надёжности default/5ms. Разность p95 без потерь относительно UDP: +45.260 мс default, +40.774 мс 5ms. Измеренная локальная скорость не является доказательством WAN-пригодности. Причины прибавки внутри реализации не установлены; нельзя приписывать всю разницу только retransmit или congestion control.

## Эксперимент 2: чувствительность к размеру записи

В исходниках испытанной pure-Go реализации найден `flushPackets`: частично заполненный пакет удерживается, пока есть неподтверждённые данные (Nagle). Для проверки зависимости повторён только канал 20 мс/направление без потерь, размер записи увеличен с 256 до 1400 байт. Остальные параметры сохранены. Это изменение нагрузки, не исправление реализации и не рекомендация padding для продукта.

| Транспорт, запись 1400 байт | p50 RTT, мс | p95 RTT, мс | p99 RTT, мс | max RTT, мс | max Write, мс |
|---|---:|---:|---:|---:|---:|
| UDP | 41.795 | 42.228 | 42.269 | 42.340 | 0.159 |
| µTP default | 60.760 | 62.299 | 99.872 | 124.614 | 42.411 |
| µTP 5ms | 60.866 | 70.993 | 106.036 | 125.440 | 42.351 |

Получены 300/300 echo во всех вариантах. Изменение размера заметно меняет результат; одного снижения congestion target недостаточно. Один вариант оказался около порога +20 мс относительно UDP, но это не проверка относительно AWG, не статистическое доказательство прохождения порога и не решение для маленьких игровых пакетов. Увеличенный размер требует большей полосы; наблюдались блокировки Write примерно на 42 мс. Причины всех выбросов и вклад Nagle отдельно не изолированы. Для дальнейшей работы нужно измерять границы записи/отправки/ACK/доставки, а не подбирать padding по одному прогону.

## Эксперимент 3: libutp и изолированное отключение Nagle

Один стенд, 256-байтовые сообщения каждые 10 мс, 300 сообщений на прогон, 20 мс задержки на направление. Три прогона на сценарий. У обеих µTP-реализаций буферы 64 KiB и target delay 5 мс. Сравнены C++ libutp через Go-обёртку и pure-Go той же зависимости; затем в отдельной временной копии pure-Go удалено только условие Nagle в flushPackets. Проверки окна, ACK и retransmit не менялись. Write обрабатывает частичную запись. Последовательные baseline и modified запуски не являются одновременными парными измерениями.

| Вариант | p95 RTT без потерь, диапазон трёх прогонов, мс | p95 RTT при настроенных 1% потерь, мс | Наибольший RTT при потерях, мс |
|---|---:|---:|---:|
| UDP | 41.924–42.201 | 42.034–42.205 | 42.548 |
| C++ libutp | 116.061–121.384 | 116.438–3163.969 | 3245.416 |
| pure-Go, исходный | 87.918–90.497 | 84.209–235.048 | 337.106 |
| pure-Go, без Nagle | 41.667–41.925 | 42.849–83.230 | 1492.944 |

Без потерь все варианты доставили 300/300 echo. При настроенных потерях UDP доставил 296/294/299; C++ libutp 299/300/300 в пределах наблюдения; pure-Go оба варианта 300/300/300. В третьем lossy-прогоне исходных µTP случайно не выпало ни одного внешнего пакета: строка с настроенными 1% не означает одинаковое фактическое число потерь. Разные варианты генерируют разное число внешних пакетов, потому фиксированные seeds не обеспечивают одинаковые потери прикладных сообщений.

Удаление Nagle воспроизводимо устранило основную прибавку p95 в данном no-loss стенде. Это причинное свидетельство вклада удержания небольших отправок, не доказательство работы полного VPN. Число внешних пакетов в no-loss прогоне выросло примерно с 273–276 до 872–876; это не равно росту байтов в том же отношении. Без Nagle сохранялись no-loss максимумы 75.593–76.644 мс, а при потерях один максимум 1492.944 мс. Плохие потери не устранены: надёжный упорядоченный поток способен задержать следующие сообщения. Сравнение с прямым AWG, BitTorrent request/piece и DPI ещё отсутствует. Порог <=20 мс добавочного RTT относительно AWG не объявляется пройденным.

Решение по исследованию: для no-loss малого пинга есть подтверждённый путь — немедленная отправка небольших записей без Nagle. Для real-time при потерях следующий предмет проверки — восстановление хвостовой потери и изоляция независимых потоков; не отключение надёжности с сохранением названия µTP. Несколько соединений могут ограничить область задержки, но не гарантируют её устранения для потока, потерявшего пакет. C++ libutp не является автоматическим исправлением задержки.

## Эксперимент 4: десять конфигураций, 120 случаев

Воспроизводимый стенд: `experiments/transport-matrix/`. Сырые данные: `results/matrix.jsonl`; полный свод: `results/summary.md`. Команда запуска и ограничения описаны в README стенда. Проверены десять конфигураций: UDP, C++ libutp, исходный pure-Go, без Nagle с target 100/5/1 мс, без Nagle с буфером 8 KiB, четыре flow-pinned соединения, дублирование внешних датаграмм и четыре соединения с дублированием. Это десять конфигураций, не десять разных протоколов.

Четыре сценария: чистый канал, независимые 1% потерь на направление, синхронные 50-мс обрывы каждую секунду, перегруженный канал 2 Мбит/с с 1% потерь и двумя фоновыми 1200-байтовыми сообщениями каждые 10 мс. Задержка 20 мс на направление. По три прогона, в каждом 400 измеряемых сообщений по 256 байт после 100 warmup-сообщений. Четыре прикладных потока закреплены за соединениями; фоновый поток попадает в lane 0. Эмулятор сериализует события в одном направлении, очереди ограничены. Loss активируется после установки соединений, поэтому устойчивость handshake к loss не измеряется. Наблюдение после отправки ограничено двумя секундами. Вызовы записи включают цельную запись с длиной, а не отдельный маленький заголовок.

Основные наблюдения:

- Чистый канал: все варианты без Nagle дали p95 41.5–41.8 мс против UDP 42.2 мс; libutp и исходный pure-Go — около 82–84 мс. Это не доказательство преимущества над UDP: величины близки к шуму планировщика.
- Независимые потери: один µTP без Nagle с дублированием внешних пакетов дал p95 41.6–41.7 мс, максимум 42.5 мс и 0/1200 пропущенных/опоздавших свыше 100 мс сообщений. Внешние байты около 1.88 MiB против 0.95 MiB без дублирования. Результат относится к независимым потерям в этой модели, не к общему обрыву пути и не к DPI-маскировке.
- Пакетные обрывы: дублирование не помогло, потому обе копии попадают в общий обрыв. Один no-Nagle поток дал p95 около 577–588 мс; четыре соединения около 326–330 мс. Максимальные RTT достигали примерно 1.4–1.55 с. В этих сценариях требование хороших игр/звонков не подтверждено.
- Перегрузка: ни один вариант не обеспечил все измеряемые потоки с приемлемой задержкой. Даже UDP имел p95 427–449 мс. Вариант четыре соединения с дублированием показал p95 доставленных 45–59 мс, но 298/1200 сообщений отсутствовали к концу наблюдения; поэтому это провал, не лучший real-time канал. Часть фоновой нагрузки и одного интерактивного потока разделяли lane 0.
- Снижение congestion target до 1 мс не является универсальным улучшением: в перегруженном сценарии этот вариант не доставил ни одного из 1200 измеряемых сообщений. Уменьшение буфера также не дало универсального решения.

Учёт проверен: 120 уникальных сочетаний variant/scenario/seed, по 400 отправленных измеряемых сообщений, Received+Missing=Sent, число RTT samples соответствует Received, Bad=0 и Reordered=0. В перегруженных случаях зарегистрировано суммарно 20999 ошибок/отказов прикладной записи, включая warmup и фоновые сообщения; точное разложение по причинам не инструментировано, поэтому их нельзя объявлять только сетевыми потерями. В остальных сценариях WriteErrors=0. Доля deadline miss считается по всем отправленным измеряемым сообщениям, включая недоставленные. Отсутствие доставки не обозначается отрицательным RTT: -1 в сырых агрегатах означает отсутствие samples.

Выбор следующего направления: базовый µTP без Nagle; ограниченная избыточность исследуется только для изолированных потерь с учётом доступной полосы. Для перегрузки необходимы приоритизация/ограничение фонового трафика до шифрования AWG и короткие очереди; для обрывов — отдельное исследование восстановления, а не уменьшение target вслепую. Измеренные варианты не удовлетворяют всему контракту продукта. Ни AWG, ни BitTorrent request/piece, ни пассивный DPI в этом стенде не проверялись; полная маскировка не заявляется.

## Панель и конфигурации

Создание, отключение, удаление клиентов; отдельный ключ на устройство, группы, IP, маршруты, ACL, лимиты скорости/трафика. Статистика разделяет полезные и внешние байты, handshake и транспортное соединение. Отзыв удаляет peer, закрывает транспорт и очищает очереди.

Версионированная строка btawg:// содержит профиль AWG, ключи, discovery/необязательные endpoints, адреса TUN, DNS, маршруты, режим транспорта и kill switch. Это секрет, не magnet и не совместимый автоматически импорт штатного AmneziaVPN. Base64 не шифрует. Импорт через stdin/защищённый файл, секреты не журналируются. В простом сценарии ключ выдаёт панель: сервер знает его при создании. Локальная генерация с регистрацией публичного ключа может быть отдельным сценарием.

Панель по умолчанию loopback с SSH-пробросом; публичная публикация требует HTTPS, аутентификации, защиты сессий/CSRF и rate limiting. Без shell API. Хранилище и backup защищают секреты; восстановление не должно молча отменять отзывы.

## Маршрутизация

Hub-and-spoke через VPS. Клиенты изолированы по умолчанию. Раздельные права на интернет, сервер и других клиентов. Stateful ACL: источник/группа, назначение/подсеть, протокол/порты. AllowedIPs проверяет адресную принадлежность, но не заменяет портовые ACL.

Подсети за клиентами включаются после одобрения администратора и проверки конфликтов; необходимы forwarding и обратный LAN-маршрут либо явный SNAT. Проверка source-IP запрещает impersonation другого peer. VPS расшифровывает A→B и заново шифрует: E2E-защита от самого VPS обеспечивается отдельно, например SSH/TLS.

Full/split tunnel, DNS внутри полного туннеля. IPv6 либо обслуживается, либо блокируется, не обходит VPN. Kill switch при отказах; внешние транспортные/discovery-сокеты исключены минимально. Не изменять чужие firewall-правила; восстановление собственных правил после аварий должно быть определено.

## Приёмка и порядок дальнейшей работы

1. Доказать транспорт до панели: direct-AWG baseline, носитель, затем AWG внутри носителя. Цель — добавочный p95 RTT <=20 мс без искусственных потерь при одинаковой нагрузке, отдельно от времени установления сессии. Измерять также first-packet-after-idle.
2. Проверить потери, jitter, ограниченную полосу, конкурирующую загрузку, несколько клиентов, реальные звонки и игровые UDP-потоки. Не ограничиваться localhost или ping. Контролировать очереди и не добавлять повторные передачи поверх уже надёжного носителя без отдельного обоснования.
3. Проверить захваты фиксированными версиями nDPI и независимого анализатора состояния BitTorrent. Разделять классификацию, согласованность протокола и статистическую различимость. Не обучать и проверять классификатор на одних захватах.
4. После удовлетворительного транспорта реализовать полный server/client, панель, отзыв, ACL, LAN routing, kill switch и IPv4/IPv6/DNS leak tests. Итог — два бинарника, не скрипт поверх третьего процесса.
5. При провале транспорта документировать конкретный предел, не скрывать его фальшивыми ACK, отключённой проверкой или переименованием протокола.
