# BTAWG MVP: сервер с веб-панелью и SOCKS5-клиент (дизайн)

Дата: 2026-11-18. Статус: на согласование владельца.

## Замысел и зачем

Два бинарника для Linux amd64/arm64: `btawg-server` (VPS) и `btawg-client`.
Сервер — хаб и шлюз с веб-панелью в стиле 3x-ui; клиент — минимальный «тупой»
узел. Цель: AmneziaWG внутри BitTorrent-носителя, обнаружение сервера строго
через DHT, и локальная оверлейная сеть между клиентами.

## Цели / не-цели / анти-цели

Цели MVP:
- Настроить на сервере AWG-профиль (внутри BitTorrent) и метод/вариант
  маскировки; создать/отозвать клиентов; скопировать строку импорта.
- Клиент на любом ПК запускается с этой строкой, находит сервер строго через
  DHT, поднимает BitTorrent-канал с AWG внутри.
- Клиент даёт SOCKS5 (без логина/пароля) как вход для приложений и реальный
  OS-интерфейс со своим IP — без системного (default-route) VPN.
- Клиенты образуют локальную сеть (client↔client через VPS).

Не-цели MVP: ACL-группы и stateful-фильтры портов, лимиты скорости/трафика,
маршрутизация подсетей за клиентами (LAN за клиентом), kill switch, IPv6,
активное зондирование/универсальная неотличимость.

Анти-цели: прямой AWG-fallback при отказе маскировки; DHT как релей данных;
обещание прохождения неизвестного DPI; фейковый µTP.

## Ограничения

- Обнаружение строго через DHT: ни клиент, ни сервер не содержат прямого
  endpoint'а друг друга; канал устанавливается только по адресу, полученному
  из DHT.
- Реальный OS-интерфейс с IP, но без default-route (не системный VPN).
- SOCKS5 — единственный вход для приложений; клиент не трогает маршруты ОС.
- Транспорт: µTP/UDP основной, TCP резерв; задержка реальных звонков/игр
  обязательна; добавка p95 ≤ 20 мс к AWG без потерь.
- Маскировка — wire-формат, не hash-корректная.
- Панель по умолчанию loopback (SSH-проброс); без shell API; секреты не
  логируются.

## Подходы (рассмотрены два)

**A. Один туннель, userspace netstack с двумя NIC.** В клиенте gVisor-netstack
владеет AWG-устройством (синтетический uplink) и отдаёт в ядро реальный TUN
(downlink); SOCKS5 и LAN терминируются в netstack. Плюс: нет egress-сервиса на
сервере. Минус: связка gVisor 2-NIC + fdbased-реальный-TUN + forwarding —
хрупкая, сложнее отлаживать.

**B. Реальный TUN + SOCKS5-цепочка на сервер (выбран).** Клиент: реальный TUN
с оверлейным IP, маршрут только на оверлейную подсеть, AWG-устройство,
SOCKS5-сервер (127.0.0.1) который «чейнится» в egress-SOCKS5 сервера по
оверлею. Сервер: AWG-хаб, egress-SOCKS5 на оверлейном IP, forwarding между
клиентами. Плюс: клиент предельно прост (без netstack), серверный egress —
стандартный SOCKS5, client↔client — штатный hub-and-spoke. Минус: нужен
egress-SOCKS5 на сервере и UDP-чейнинг (стандартно, но больше кода).

Выбран **B**: ровно соответствует «клиент умеет только SOCKS5 + реальный
интерфейс с IP», ниже риск, чем A.

## Архитектура

### Клиент (`btawg-client`)

1. Создаёт реальный TUN `btawg0` с оверлейным IP (например 10.77.0.2/24);
   добавляет маршрут только `10.77.0.0/24` → `btawg0`. Default-route НЕ ставится.
2. AWG-устройство привязано к этому TUN; `conn.Bind` = BitTorrent-носитель
   (extended/request-piece over µTP/TCP). Peer у клиента один — сервер,
   `allowed_ip = 0.0.0.0/0` (всё идёт через сервер; сервер разводит).
3. SOCKS5-сервер (без auth) слушает `127.0.0.1:1080`. Для CONNECT и UDP
   ASSOCIATE клиент «чейнится» в egress-SOCKS5 сервера (`10.77.0.1:1080`) по
   оверлею: DNS-резолв и выход в интернет делает сервер (защита от DNS-leak).
4. Никакого netstack в клиенте; SOCKS5 и оверлей идут через ядро и один TUN.

Потоки:
- Интернет: приложение → SOCKS5(127.0.0.1) → оверлей → сервер-egress → интернет.
- Client↔client: приложение → маршрут 10.77.0.x → `btawg0` → AWG → сервер →
  перешифрование → клиент B (без SOCKS5, «как в LAN»).

### Сервер (`btawg-server`)

1. AWG-хаб: реальный TUN (или netstack) с IP `10.77.0.1`; peer на каждого
   клиента (`allowed_ip = <клиентский IP>/32`); `ip_forward` + маршрут оверлея —
   для client↔client (A→B расшифровывается и перешифровывается на хабе).
2. egress-SOCKS5 (без auth) на `10.77.0.1:1080` — выход клиентов в интернет;
   слушает только оверлейный адрес (достижим лишь через туннель).
3. BitTorrent-носитель: слушатель (µTP/TCP accept) на внешнем порту; каждый
   клиент — одно BT-соединение с handshake и AWG-датаграммами.
4. DHT-нода (BEP 5): генерирует infohash, анонсирует в DHT `(внешний IP, порт
   носителя)` под этим infohash; периодический re-announce.
5. Веб-панель (3x-ui style) на loopback: логин, конфиг сервера, клиенты.

### Обнаружение (строго DHT)

- Сервер: `announce_peer(infohash, ip, port)` в публичном DHT.
- Внешний IP сервер определяет как IP интерфейса с default-route (переопределяется
  в панели для NAT); порт анонса — порт BitTorrent-носителя. DHT-порт и порт
  носителя — разные UDP/TCP-порты.
- Клиент — lookup-only DHT-клиент (не обслуживает других): bootstrap через
  публичные узлы (зашиты в бинарник: router.bittorrent.com,
  dht.transmissionbt.com, router.utorrent.com и др.), `get_peers(infohash)` →
  адрес сервера → dial носителя → BT-handshake (тот же infohash).
- Недоступность DHT → явная ошибка discovery (не молчаливое зависание).
- infohash — полупубличный локатор: кто его знает, может узнать IP:порт сервера,
  но без AWG-ключей канал не вскрыть.

### Носитель и маскировка

- Дефолт: **extended (BEP 10) over µTP no-Nagle** (валидировано: +0.07 мс к AWG,
  nDPI=BitTorrent без риск-флагов).
- Альтернативы (из FINDINGS.md, все nDPI=BitTorrent): request/piece over µTP
  no-Nagle, request/piece over TCP, extended over TCP.
- Webseed исключён (nDPI=HTTP), bare-AWG fallback исключён.
- Конфиг сервера выбирает метод+вариант; строка импорта несёт тот же выбор.

### Конфиг-строка `btawg://`

`btawg://` + base64url(JSON). Секрет (содержит приватный ключ клиента). Поля:
version, infohash, server_pubkey, client_privkey, client_pubkey, client_ip,
subnet, server_ip, transport (метод+вариант), socks_port, awg_profile
(jc/jmin/jmax/s1-4/h1-4), опц. bootstrap-узлы. **Без endpoint'а сервера.**

### Веб-панель (эталон 3x-ui)

Экраны: вход (логин/пароль), дашборд (статус туннеля, счётчики: внутренние/внешние
байты, handshake, соединения), «Настройки сервера» (AWG-профиль, оверлейная
подсеть, метод/вариант маскировки, порты SOCKS5/панели), «Клиенты» (список,
создать → строка импорта, отозвать, статус подключён/последняя активность).

### Хранилище и безопасность

- bbolt (встроенное, транзакционное), файл с правами 0600; пароль панели —
  bcrypt/argon2; сессии cookie + CSRF + rate-limit логина.
- Панель loopback по умолчанию; публичная публикация — только через HTTPS+auth
  (вне MVP).
- Отзыв клиента: удалить peer, закрыть BT-соединение, очистить очереди.

## Решения владельца (зафиксированы)

- Обнаружение и установка канала — строго через DHT, без прямых endpoint'ов.
- Реальный OS-интерфейс с IP, но без системного TUN (нет default-route).
- SOCKS5 без логина/пароля — единственный вход приложений.
- Client↔client включён сразу.
- MVP = hub-and-spoke (вариант 1 ранее), SOCKS5-клиент вместо системного VPN.

## Честные ограничения

- Проверено только против nDPI (пассивный), офлайн-pcap с синтетическими
  L3/L4-заголовками; активное зондирование вне скоупа.
- Wire-формат без hash-корректности: AWG-шифротекст подменяет блоки файла.
- Публичный DHT может быть заблокирован/троттлится тем же DPI — тогда discovery
  падает явно (план B: собственные bootstrap-ноды, отдельным шагом).
- Реальный WAN/VPS и поведение при потерях не проверялись в стенде clean40.
